## Purpose

Requirement 1 — *install and maintain network security controls* — as Marketa implements it. This document is the standard, not a restatement of the standard. Where the requirement says an entity must define configuration standards, this document contains Marketa's configuration standards. Where it says services, protocols and ports must carry a business justification, this document contains the justifications, including the uncomfortable ones.

It covers **1.2.1** through **1.2.8**, **1.3.1** to **1.3.3**, the **1.4** family including anti-spoofing, and **1.5.1**. Requirement 1.1.1 and 1.1.2 — documented, maintained, in-use processes with assigned roles — are discharged by the governance model in Phase 01 and are cross-referenced rather than restated.

## 1. What v4.0 Changed, and Why the Vocabulary Matters

PCI DSS v4.0 renamed Requirement 1 from *firewalls and routers* to **network security controls**. The change is not cosmetic and it is the reason Marketa's standard is written the way it is.

| v3.2.1 framing | v4.0.1 framing | Consequence for Marketa |
|---|---|---|
| Firewalls and routers | **Network security controls (NSCs)** — any technology enforcing policy at a network boundary | A security group is an NSC. A VLAN access control list is an NSC. A cloud network firewall is an NSC. A wireless controller enforcing an SSID-to-VLAN mapping is an NSC. **A switch trunk allowed-VLAN list is an NSC** |
| A device-centric requirement | A **function**-centric requirement | The standard applies to the nine components in group G10 by what they do, not by what the vendor calls them |
| DMZ as a named construct | The construct survives; the language generalises | Marketa's internet edge still has a DMZ, and 1.4.4 still says systems storing cardholder data are not directly accessible from untrusted networks |

The practical significance is that Marketa's NSC inventory contains items an entity working from a v3.2.1 habit would not have listed. All nine components in **group G10** are NSCs; so, for the purposes of 1.2.1 and 1.2.8, are the infrastructure-as-code pipeline **CT-30** that generates the Z2 boundary configuration and the AWS organisation control plane **CT-41** that can override it.

The NSC inventory under this standard is **eleven components**: three stateful firewall clusters (CT-43, CT-44, CT-45); the layer-3 switching layer enforcing CDE VLAN access control lists (CT-46); WAN and SD-WAN policy enforcement (CT-47); the store-estate VLAN and ACL policy source (**CT-48**); the wireless LAN controller enforcing SSID-to-VLAN policy (**CT-49**); the cloud network firewall and security-group control plane (CT-50); cloud routing control (CT-51); and the two NSC configuration generators and override paths, CT-30 and CT-41.

## 2. Configuration Standards — 1.2.1

Requirement 1.2.1 obliges configuration standards for NSC rulesets to be defined, implemented and maintained. Marketa's standard is expressed as fourteen mandatory settings, each with a verification method, applied to every NSC in the inventory. A device that cannot meet a setting is recorded as an exception with a compensating control and a review date; there are two such exceptions and both are named.

| # | Standard | Applies to | Verification |
|---|---|---|---|
| **NSC-01** | Management plane on a dedicated out-of-band management VLAN, reachable only from Z3 privileged access paths | All 11 | Configuration extract, monthly |
| **NSC-02** | Authentication to the device via centralised AAA with individual accounts; no shared credentials; local accounts limited to a single sealed break-glass credential held in CT-14 | All 11 | AAA server records; local account enumeration |
| **NSC-03** | MFA for all administrative access under **8.4.2** and **8.4.3** | All 11 | Session records from CT-11 |
| **NSC-04** | Vendor defaults removed — default accounts disabled or renamed with changed credentials, default SNMP community strings removed, default certificates replaced, unused management services disabled. **2.2.2 and 2.3.1** | All 11 | Configuration extract; authenticated scan from CT-31 |
| **NSC-05** | Only SSHv2, HTTPS with TLS 1.2 or above, and SNMPv3 with authPriv enabled for management; Telnet, HTTP and SNMPv1/v2c disabled on the management plane | All 11 | Configuration extract; port scan from an adjacent segment |
| **NSC-06** | Every policy terminates in an explicit **deny-and-log** rule. Implicit deny is not accepted as evidence of a deny, because it produces no log | All 11 | Rule-base extract; the terminating rule's hit counter |
| **NSC-07** | Every rule carries five metadata fields — identifier, business justification, requesting owner, approval reference, review date. A rule missing any of the five is quarantined at the next 1.2.7 review | All 11 | Rule-base extract with metadata completeness assertion |
| **NSC-08** | No `any` in the source, destination or service field of any rule on a **T1 boundary**. On non-T1 boundaries an `any` requires documented justification and a review date under 1.2.5 | CT-43, CT-45, CT-46, CT-50 absolutely; others conditionally | Automated rule-base assertion, nightly |
| **NSC-09** | Object naming convention enforced; no address literals in rules; decommissioned objects removed within 30 days | All 11 | Object reconciliation against IPAM CT-63 |
| **NSC-10** | Logging to CT-20 and onward to CT-18 for all permit and deny events at T1 boundaries; connection setup and teardown logged; log delivery health monitored under **10.7.2** | All 11 | Heartbeat reconciliation; log volume banding |
| **NSC-11** | Time from CT-62 only, under **10.6.1** to **10.6.3** | All 11 | Configuration extract |
| **NSC-12** | Configuration backed up on change to the version-controlled configuration store; **running configuration compared to stored configuration daily**, with divergence raised as an incident | All 11 | Drift report — see §7 |
| **NSC-13** | Switch ports serving an out-of-scope zone configured as access ports with an explicit VLAN, port security enabled, and unused ports administratively shut and assigned to a black-hole VLAN. **Trunk ports carry an explicit allowed-VLAN list; a trunk with no allowed-VLAN list is a defect, not a default** | CT-46, CT-48-managed store switches | Configuration extract; port-role assertion |
| **NSC-14** | Firmware and software maintained within the vendor's supported range; security patches applied within one month under **6.3.3** | All 11 | Version telemetry; authenticated scan |

**NSC-13 is stated in those terms because of what 03.07 found.** A trunk port with no allowed-VLAN list permits every VLAN defined on the switch, which is a platform default rather than an administrator's decision, and which no rule-base review will surface because it is not a rule. The standard was rewritten to make the absence of an allowed-list a positive defect with an assertion behind it. That rewrite is a consequence of the penetration test, and the document records the sequence honestly: **the standard did not contain NSC-13 in this form before 2026-05-15.**

### 2.1 The two exceptions

| Exception | Component population | Standard not met | Compensating position | Review |
|---|---|---|---|---|
| **NSC-EX-01** | 496 store-estate appliances of a generation that does not support SNMPv3 | NSC-05 — SNMPv2c remains in use for read-only monitoring | Read-only community, non-default string rotated quarterly, restricted by ACL to the CT-48 polling addresses, on the management VLAN only, with the security features under **1.2.6** applied | Replacement in the FY2027 store refresh; reviewed quarterly until then |
| **NSC-EX-02** | 9 vendor-locked POS back-office appliances under constraint **CON-03** | NSC-02 and NSC-14 partially — the vendor retains a support account and controls the firmware cadence | Vendor account disabled between support windows and enabled by ticket; sessions brokered through CT-11 and recorded; firmware tracked in the TPSP review | Tied to open item **OI-02-02**, due 2027-01-31 |

Both exceptions are recorded with the requirement they do not meet, rather than described as met by an alternative. That distinction matters: **an exception with a compensating position is a known gap under management; a redefinition of the standard to fit the estate is a gap that has been made invisible.**

## 3. Services, Protocols and Ports — 1.2.5

Requirement 1.2.5 obliges the entity to identify, approve and record a defined business need for every service, protocol and port allowed. Marketa's register holds every allowed service on every T1 boundary and every non-default allowance elsewhere.

| Service / protocol / port | Where allowed | Business need | Owner | Review |
|---|---|---|---|---|
| HTTPS 443, mutually authenticated | NF-11, NF-12, NF-13, NF-20 | Provider APIs and the acquirer file exchange; the token and order feed from Z8 | Elena Marchetti | Six-monthly |
| SSH 22, brokered only | NF-01 | Administrative session to Z1 hosts, never direct | Trevor Kim | Six-monthly |
| RDP 3389, brokered only | NF-01 | Administrative session to Z1 Windows components | Trevor Kim | Six-monthly |
| LDAPS 636, Kerberos 88 | NF-06 | Directory authentication for Z1 components | Trevor Kim | Six-monthly |
| Syslog over TLS 6514 | NF-05 | Audit log forwarding under 10.2.x | Marcus Hale | Six-monthly |
| NTP 123 to CT-62 only | NF-09 | Time synchronisation under 10.6.x | Trevor Kim | Annual |
| DNS 53 to CT-61 only | NF-09 | Name resolution; no external resolver reachable from Z1 | Trevor Kim | Annual |
| Backup transport, vendor port | NF-08 | Backup of Z1 components to CT-34 and CT-35 | Trevor Kim | Six-monthly |
| IPsec ESP and IKEv2 | NF-10 | Z1 to Z2 replication | Trevor Kim | Six-monthly |
| Agent protocols — EDR, FIM, configuration management | NF-02, NF-04 | Security agent control from Z3 | Marcus Hale | Six-monthly |
| Scanner protocol, credentialed | NF-03 | Authenticated internal scanning under 11.3.1.2 | Marcus Hale | Six-monthly |

Two disciplines make the register worth maintaining.

**A justification names a business outcome, not a system.** "Required by the backup product" is not a justification; "restoration of CDE-02 within the recovery objective the payment operations continuity plan states" is. The distinction is the difference between a register that can be reviewed and one that can only be re-read.

**A flow with no owner is removed, not investigated indefinitely.** Phase 02 found 31 rules touching Z1 or Z2 with no documented justification. All 31 were removed rather than being carried on a list of items to research, and none of the removals caused an incident — which is the usual outcome and the reason the practice is now standing.

## 4. Change Control — 1.2.2

Requirement 1.2.2 obliges all changes to network connections and to NSC configurations to be approved and managed in accordance with the change control process in **6.5.1**. Marketa's process adds a segmentation-specific layer, because principle **SP-8** treats a boundary change as a scope event.

| Stage | Control | Evidence |
|---|---|---|
| Raise | Change classified against the segmentation-affecting change list in §4.1. Classification is a mandatory field and cannot be left blank | Change record |
| Review | A segmentation-affecting change requires a **scope-delta review** — which zones, which flows, which conditions in the register are touched, and whether the assessed population changes | Scope-delta record, `templates/` |
| Approve | Segmentation-affecting changes require approval from the zone owner **and** from the Payment Card Compliance Manager. Approval by the requester's own management is not sufficient | Change record with two named approvers |
| Implement | Applied from a privileged path only, brokered through CT-11 and recorded | Session recording |
| Verify | Post-change verification includes a targeted reachability test of the affected boundary, not only a functional test of the intended flow | Test output |
| Close | **1.2.3 and 1.2.4 diagram updates are completion criteria.** A change closed without them is reopened | Diagram revision history |
| Re-test | If the change is on the re-test trigger list, an **11.4.5** re-test obligation is raised automatically | Re-test register |

### 4.1 What counts as a segmentation-affecting change

| Change type | Segmentation-affecting? | 11.4.5 re-test required? |
|---|---|---|
| New rule, or modification of a rule, on a T1 boundary | Yes | **Yes** |
| Rule change on a non-T1 boundary policy | Yes | Assessed case by case; yes where it alters what a zone can reach |
| New VLAN, or change to a VLAN-to-port assignment, in any store | Yes | **Yes**, for the affected boundary |
| Change to a trunk allowed-VLAN list anywhere in the estate | **Yes** | **Yes**. Added 2026-06 following 03.07 |
| SSID creation, deletion, or change to an SSID-to-VLAN mapping or switching mode | **Yes** | **Yes**. Added 2026-06 following 03.07 |
| Route table, route propagation or transit gateway attachment change in AWS | Yes | **Yes** — the RCH-01 class of change |
| Security group or NACL change affecting Z2 | Yes | Yes |
| Merge to the CT-30 infrastructure-as-code repository touching boundary resources | Yes | **Yes**, raised automatically by the pipeline |
| Service control policy or account boundary change in the AWS organisation CT-41 | Yes | Yes |
| Store build image revision affecting network configuration | **Yes** | **Yes**. Added 2026-06 following 03.07 |
| Firmware or software upgrade of an NSC | Yes | Assessed; yes where the platform's default behaviour changes |
| Application change with no network effect | No | No |

**Four rows on that list were added in June 2026.** Each was added because the May penetration test demonstrated a change class that could open a boundary and that Marketa's change process did not previously classify as segmentation-affecting. The store build image row is the most consequential: a build image is a change to 482 networks executed once, and it was being managed as a platform-engineering artefact rather than as a network change.

## 5. Inbound and Outbound Restriction — 1.3.1 and 1.3.2

| Requirement | Obligation | Marketa's implementation |
|---|---|---|
| **1.3.1** | Inbound traffic to the CDE restricted to necessary traffic; all other traffic denied | Sixteen named flows cross a T1 boundary; **four** of them are inbound to Z1 from Z3 and two inbound to Z2. Every other inbound source is denied at CT-43, CT-46 and CT-50, with a terminating deny-and-log under NSC-06 |
| **1.3.2** | Outbound traffic from the CDE restricted to necessary traffic; all other traffic denied | Outbound is written with the same discipline. Z1 initiates to five Z3 service endpoints and two external providers. **No general internet egress exists from Z1 or Z2**; Z2 has no internet gateway at all |

The outbound limb is the one merchants under-implement, and 02.07 §4.3 explains why in Marketa's own estate: before remediation, a Z1 component could reach a Z4 internet proxy to retrieve operating-system updates. Nobody had thought of it as a CDE boundary crossing because it was filed under "patching."

> **A flow named after its business purpose stops being examined as a network path.** Patching, backup, monitoring and replication are the four labels under which unexamined boundary crossings live. Marketa's rule is that the 1.2.5 register records the *network* description of a flow — source, destination, protocol, port, direction, initiator — and the business label is metadata, not identity.

Outbound restriction is also the exfiltration control. A CDE that can only initiate to seven named destinations, all logged and inspected, is an environment in which an attacker's egress options are visible before they are used. That property is worth more than the small inconvenience it imposes on engineering, and it is the reason **NF-07** exists as a single-endpoint patch pull rather than as a proxy allowance.

## 6. Insecure Services and Protocols — 1.2.6

Requirement 1.2.6 obliges security features to be defined and implemented for all services, protocols and ports in use that are considered insecure. The requirement does not prohibit them. It obliges the entity to know it is using them and to say what compensates.

Marketa's register is honest about an estate of this age and shape.

| Service | Where in use | Why still in use | Security features implemented | Target |
|---|---|---|---|---|
| **SNMPv2c** | 496 store-estate appliances; read-only monitoring | The appliance generation predates SNMPv3 support and replacement is a 482-site hardware programme | Read-only community; non-default string rotated quarterly; ACL restricting the source to CT-48 polling addresses; management VLAN only; write access disabled at the platform | FY2027 store refresh |
| **TFTP** | Store switch imaging during build and recovery only | The platform's recovery path requires it | Disabled in steady state; enabled by change record for a defined window; source-restricted to the on-site engineering address; imaging server on the management VLAN with no route beyond it | Retained with controls |
| **NetBIOS and SMB name resolution** | Z4 and Z5 legacy file and print | Application dependencies in inventory and workforce tooling | SMBv1 disabled estate-wide; signing enforced; blocked at every zone boundary; not permitted on any T1 boundary in either direction | Application remediation, Phase 04 |
| **LDAP without TLS** | Two legacy Z4 applications | Vendor products without LDAPS support | Confined to Z4; blocked at the Z3 boundary; the directory rejects simple binds from outside a named source list | Vendor upgrade, FY2027 |
| **HTTP** | Redirect listeners on the internet edge | Redirect-to-HTTPS only | No content served; HSTS on the redirect target; no credential or data accepted over the listener | Retained with controls |
| **Wireless PSK, legacy** | **214 devices** — see 03.06 §6 | A pre-2022 store device population that cannot join the 802.1X network | Confined to a dedicated internet-only VLAN; key rotated; the population inventoried and shrinking; **recorded as a known weakness and tracked to corrective action CAP-05** | Elimination programme; Phase 06 |

The last row is the one the programme wants a reader to notice. It is a known weakness, it is written down here in the standards document rather than discovered later, and it becomes a formal corrective action item in the programme's remediation tracking. Foreshadowing a weakness is not the same as excusing it: **214 devices holding a shared static key are 214 devices that share a compromise.**

## 7. Configuration File Security and Drift — 1.2.8

Requirement 1.2.8 obliges NSC configuration files to be secured from unauthorised access and **kept consistent with active network configurations**. The second limb is the interesting one and it is where Marketa's standard changed most in this phase.

| Control | Implementation |
|---|---|
| Storage | All NSC configurations held in a version-controlled configuration store with access restricted to the network engineering group and read access to Internal Audit. No configuration file on an engineer's workstation, in a ticket attachment, or in a shared mailbox |
| Access | Authenticated, individually attributed, MFA-protected, logged to CT-18 |
| Integrity | Signed commits; change attributable to a named engineer and a change record |
| Backup | Configuration captured on every change and on a nightly schedule |
| **Consistency — the 1.2.8 second limb** | **Running configuration is retrieved from every NSC daily and compared against the stored configuration. Any divergence raises an incident, not a report** |
| Cloud equivalent | The Z2 boundary is defined in the CT-30 infrastructure-as-code repository; drift is detected by continuous plan-diff against deployed state, and manual console changes to boundary resources are denied by service control policy |

**Daily drift detection did not exist across the store estate before this phase, and its absence is the direct enabler of the 03.07 finding.** The store-estate policy controller CT-48 held an *intended* policy. The switch at the affected store held a *running* configuration that differed from it. Phase 02's reachability computation was built from the controller's intended policy, because that is the artefact a policy controller exposes, and it therefore modelled a network that did not exist at that one site.

| What was compared, before | What is compared, now |
|---|---|
| Controller intent versus the zone model | Controller intent versus the zone model, **and** running configuration versus controller intent, **and** observed VLAN membership versus expected VLAN membership |
| Weekly, on a sample of stores | **Daily, all 482 stores, all switch ports** |
| Divergence reported | Divergence raises an incident with a four-hour response target |
| Trunk allowed-VLAN lists not compared | Trunk allowed-VLAN lists compared explicitly, with an assertion that the list is present and non-empty |

## 8. NSC Ruleset Review — 1.2.7

Requirement 1.2.7 obliges the configurations of NSCs to be reviewed **at least once every six months** to confirm they are relevant and effective. This is not an entity-defined frequency, so no targeted risk analysis under 12.3.1 arises; the cadence is fixed by the standard.

Marketa's review cycle was stood up as open item **OI-02-06**, following the Phase 02 rule-base analysis that found 1,286 shadowed rules in a base of 11,847 — an 11% dead-rule rate that, as 02.07 §4.1 put it, is the strongest available evidence that the base had not been reviewed in the way 1.2.7 contemplates.

| Review element | Method | Output |
|---|---|---|
| Rule relevance | Every rule tested against its recorded business justification and its owner re-confirmed. Unclaimed rules quarantined for 30 days, then removed | Quarantine and removal log |
| Rule effectiveness | Hit-counter analysis. A rule with zero hits in six months is challenged; a **deny** rule with zero hits is challenged differently, because it may mean the traffic is being permitted earlier | Hit analysis |
| Shadowing and redundancy | Automated analysis for rules unreachable behind an earlier rule | Shadowed-rule report |
| Permissiveness | Assertion against NSC-08; any `any` on a T1 boundary is a defect | Permissiveness report |
| Object hygiene | Objects reconciled against IPAM CT-63; decommissioned objects removed | Object reconciliation |
| Metadata completeness | Assertion against NSC-07's five fields | Completeness report |
| Cloud rulesets | Security groups, NACLs, network firewall rule groups and route tables reviewed on the same cycle, from the deployed state rather than from the IaC source | Cloud review record |

| Cycle | Period | Rules reviewed | Removed | Tightened | Reviewer | Approver |
|---|---|---|---|---|---|---|
| 2026 H1 | Phase 02 rule-base rationalisation, treated as the first cycle | 11,847 | 1,719 — 1,286 shadowed, 402 stale objects, 31 unjustified | 47 overly permissive rules narrowed; 16 justified and dated | Trevor Kim's team | Naomi Bhatt |
| 2026 H2 | Standing cycle, commenced 2026-08 | 10,128 | Reported in Phase 06 | Reported in Phase 06 | Network engineering, independent reviewer | Naomi Bhatt |

The second cycle is performed by an engineer who did not author the rules under review. Independence within a review is a small discipline with a disproportionate effect: **an author reviewing their own rule base tests the rules they remember writing.**

## 9. Wireless — 1.3.3

Requirement 1.3.3 obliges NSCs to be installed between all wireless networks and the CDE, **regardless of whether the wireless network is itself a CDE**, such that wireless traffic to the CDE is denied or, where necessary for a business purpose, only authorised traffic is permitted.

| Wireless network | Business purpose | Path to the CDE | Enforcement |
|---|---|---|---|
| Store guest wireless — **Z7** | Customer amenity | **None permitted** | Anchored to CT-49 and tunnelled to a dedicated internet break-out; client isolation; no Z7 VLAN present on any store switch port serving Z5 or Z6 |
| Store colleague wireless | Handheld inventory and workforce devices | None to Z1 or Z2; a named flow set to Z5 services only | 802.1X with certificate-based authentication; dynamic VLAN assignment into a colleague VLAN inside Z5 |
| Corporate wireless — Columbus and Austin | Staff computing | None to Z1 or Z2. Reaches Z3 only through the B-04 administrative entry path | 802.1X; the wireless client is a Z4 member and inherits Z4's boundary position |
| Distribution centre wireless | Warehouse handhelds | None | 802.1X; dedicated VLAN within Z4 |

The full wireless position — defaults under **2.3.1**, encryption keys under **2.3.2**, quarterly detection of unauthorised access points under **11.2.1**, and the authorised-AP inventory under **11.2.2** — is 03.06.

## 10. Trusted and Untrusted Networks — the 1.4 Family

| Requirement | Obligation | Marketa's implementation |
|---|---|---|
| **1.4.1** | NSCs implemented between trusted and untrusted networks | CT-44 at the internet edge; CT-49 and CT-48 between Z7 and everything else; CT-50 at the cloud boundary; CT-47 at the WAN aggregation point. Marketa's trust register in 03.02 §2.1 states which networks are untrusted, so the question is never argued at implementation time |
| **1.4.2** | Inbound traffic from untrusted networks to trusted networks restricted to communications with system components providing publicly accessible services, protocols and ports, plus stateful responses; all other traffic denied | The only publicly accessible Marketa services are the Z8 storefront edge and the Z2 webhook endpoint that receives Truvance callbacks. Both terminate in a DMZ construct at CT-44 or CT-50; neither is in Z1; stateful inspection is enforced and asymmetric paths are eliminated by design |
| **1.4.3** | **Anti-spoofing measures** implemented to detect and block forged source IP addresses from entering the trusted network | Unicast reverse-path forwarding in strict mode on all internet-facing and WAN-facing interfaces; bogon and RFC 1918 ingress filtering at CT-44 and CT-47; ingress access lists at every store WAN interface rejecting source addresses that do not belong to that store's allocation; on AWS, VPC source/destination checking left enabled on every interface and disabled only where a documented network function requires it, of which there are none in Z2 |
| **1.4.4** | System components storing cardholder data are not directly accessible from untrusted networks | CDE-02 and CDE-08 hold truncated PAN and tokens; neither is reachable from any untrusted network by any path. CDE-03 and CDE-04 process full PAN and are reachable only from Z3 named flows. **There is no publicly accessible interface on any Z1 or Z2 component** |
| **1.4.5** | Disclosure of internal IP addresses and routing information limited to authorised parties | NAT at the internet edge; split-horizon DNS with no internal records in the external zone; no internal addressing in error pages, mail headers, or public certificates; route filtering at every eBGP boundary; AWS resource identifiers and private addressing excluded from customer-facing responses |

A note on 1.4.3 that the programme records because it is a common gap: **anti-spoofing on the WAN side is more valuable to Marketa than on the internet side.** The internet edge is well filtered and heavily watched. The store WAN carries 482 sites of traffic into an aggregation point, and a forged source address arriving from a store link is a far more plausible attack than a forged address arriving from the internet. Every store WAN interface therefore carries an ingress filter permitting only that store's own allocation, and the filter is generated from IPAM rather than maintained by hand.

## 11. Devices Connecting to Both Untrusted Networks and the CDE — 1.5.1

Requirement 1.5.1 obliges security controls on any computing device — company-owned or employee-owned — that connects both to untrusted networks and to the CDE. It is the requirement that governs the laptop that is on hotel Wi-Fi in the morning and administering a payment system in the afternoon.

Marketa's structural answer is that **no device connects to both**. An administrator's laptop is a Z4 member; it reaches a Z3 jump host with MFA; the session continues from the jump host. The laptop never has a network path into Z1 or Z2. That is the basis on which ~1,100 endpoints are excluded from the assessment, and it is the largest single exclusion in the determination.

The requirement still applies, because the population that administers the boundary is the population 1.5.1 is about.

| Control | Implementation | Population |
|---|---|---|
| Host firewall with a managed, non-user-modifiable policy | Enforced by CT-27; drift alerts to CT-18 | All administrative endpoints |
| EDR with tamper protection, managed from CT-23 | Agent health monitored under 10.7.2; a device out of contact for 24 hours loses network authorisation | All administrative endpoints |
| No split tunnelling while a remote-access session is active | Enforced at CT-12 | All remote administrative access |
| Full-disk encryption and screen-lock policy | Enforced by CT-27 | All administrative endpoints |
| Device certificate and posture check before 802.1X authorisation or VPN admission | Enforced at CT-12 and the wireless infrastructure | All administrative endpoints |
| **No clipboard, drive mapping or file transfer through the jump host** under **3.4.2** | Enforced at CT-08, CT-09, CT-10; verified by test rather than by setting | All CDE administrative sessions |
| Administration of NSCs, including CT-48, only from a privileged access workstation brokered through CT-11 | Enforced by ACL on the management plane under NSC-01 | NSC administrators |

The last row is condition **SEG-C5**, and 02.08 §12 flagged it against CT-48 specifically: the controller that determines the segmentation state of 978 store systems and 1,914 POI devices is administered from workstations that also carry general network access. The Phase 05 access-control work is where the privileged access workstation model is fully specified; the network-side enforcement is here.
