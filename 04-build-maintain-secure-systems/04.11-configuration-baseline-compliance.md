## Purpose

**04.01 is the standard. This document is the evidence that the standard is deployed.**

Requirement 2.2.1 obliges configuration standards to exist, to cover all system components, and to be **applied when new systems are configured and verified in place before or immediately after a component is connected to a production environment.** The second half of that sentence is where an assessment is won or lost, and it is not a documentation obligation. It is a measurement obligation.

This document reports the measured deployment of **BL-WIN, BL-LNX, BL-NET, BL-AWS, BL-DB and BL-APP** across the **71 assessed system components**: how compliance is measured, what **CA-1 to CA-6** actually produced in the operating period, how divergence and exception are handled, what cannot be measured the standard way and what is substituted for it, and how the whole thing will be sampled in November.

It is written on a principle Phase 03 learned expensively and 04.01 restates in its first line:

> **A baseline document is not a control. The deployed state is the control, and measuring it is what makes the claim real.**
>
> Build image SB-4.1 was correctly authored, correctly gated, correctly deployed to 482 stores, and carried a trunk with no allowed-VLAN list for eighteen months. Every document about it was accurate. Nothing measured the thing the documents described.

## 1. What Is Being Measured, and Against What

| Dimension | Position |
|---|---|
| Population | **71 assessed system components** — 8 CDE, 63 connected-to and security-impacting, per 02.09 |
| Standard | The six baselines and the eleven mandatory controls **SCS-01 to SCS-11** in 04.01 §2.1 |
| Mechanism | **CA-1 to CA-6**, the configuration assertion set — the direct extension of Phase 03's **DA-1 to DA-6** network drift assertions |
| Measurement period | **2026-04-10 to 2026-07-15**, 96 days |
| Unit of measurement | The **baseline item** on a **running component**, not the baseline document and not the build template |
| Definition of compliant | Every machine-verifiable item of the component's assigned baseline asserts true, with any divergence either auto-remediated inside its window or carrying a registered exception |
| Definition of a claim | 04.01 §1: **a setting Marketa cannot machine-verify on a running component is a setting Marketa does not claim.** Non-verifiable items are counted separately, inspected on a named date by a named person, and reported as inspection evidence rather than folded into an assertion rate |

## 2. The Three Measurement Classes

Not every component can be measured the same way, and pretending otherwise produces a compliance percentage that quietly averages a strong control with an absent one. Marketa splits the 71 explicitly.

| **Class B — observed** | **9** | The **CON-03** vendor-locked POS back-office appliances. They are inspected, dated, attributed and reported as inspection evidence. **Counting them inside an assertion rate would inflate the rate with items no machine ever tested.**

## 4. The Seventy-Four, and What They Say

| Class | Count | Character | Handling |
|---|---|---|---|
| Reversible parameter drift | **61** | Screen-lock timeouts reset by a policy refresh, audit sub-category settings reverted by a platform update, cipher-suite ordering changed by an agent upgrade | Auto-remediated within the hour and ticketed for cause analysis. Auto-remediation is permitted **only** for reversible settings on an explicit list; nothing on the SCS-05, SCS-06 or SCS-11 path auto-remediates |
| Unexpected listeners | **9** | 7 were a monitoring agent's diagnostic port enabled by an upgrade default; 1 a debug listener on a pre-production build promoted in error; 1 a vendor management daemon re-enabled by firmware | Incident. A Z1 or Z2 unexpected listener is a **P2**. All 9 closed; the agent upgrade default was corrected at source so it could not recur across the fleet |
| Vendor default credentials reintroduced | **3** | All three by appliance firmware updates | Credential rotated within 24 hours; the class added to the **SIG-2** significant-change rationale in 04.08 §4.1; CA-4 frequency raised to daily following any firmware event on an appliance component |
| Silence | **1** | A Z1 host that stopped reporting for four days after a hypervisor migration, found to have been **rebuilt from a stale image** | The most valuable finding of the period. §4.1 |

### 4.1 The stale image, and why silence is a finding

A component rebuilt from a stale image passes every functional test it is given. The application starts, the health check succeeds, the load balancer returns it to service, and the monitoring dashboard turns green. It fails only **SCS-03** — the baseline verified in place before the component reaches a production network — and SCS-03 is not something a functional test looks at.

It was caught by **CA-1's silence rule**, which treats a component that stops reporting as failing until proven otherwise. Three consequences were taken from it.

| Consequence | Change |
|---|---|
| The rebuild path was not gated | Hypervisor-level rebuild now resolves the image reference at build time rather than from a cached local template, and the build gate at SCS-03 runs on the rebuilt instance before it is returned to service |
| The gap was four days, not four hours | CA-1's escalation was tightened: 24 hours of silence on a Z1 or Z2 component is now a P2, not a report line. On connected-to components it remains 72 hours |
| Nobody had asked what silence meant | Recorded in the standard: **a control that reports nothing looks exactly like a control with nothing to report.** Phase 03 learned this on the network plane; Phase 04 learned it again on the configuration plane, which suggests it is a property of assurance rather than of networks |

### 4.2 Detection and remediation timing

| Measure | Class A | Notes |
|---|---|---|
| Median time from divergence to detection | **9 hours** | Bounded by the daily assertion cycle. The honest ceiling is 24 hours for CA-2 and CA-3, and 7 days for CA-4 and CA-6 |
| Median time from detection to remediation, auto-remediable | **41 minutes** | 61 of 74 |
| Median time from detection to remediation, ticketed | **2.1 days** | Longest 9 days, an appliance requiring a vendor maintenance window |
| Divergences open longer than their SLA at 2026-07-15 | **0** | |

The 9-hour median is reported alongside its 24-hour and 7-day ceilings because a median hides the tail, and the tail is what an adversary occupies. **The correct statement is not "we detect drift in nine hours". It is "no configuration divergence on a CDE component can persist for more than 24 hours undetected, and no default-credential reintroduction for more than seven days"** — and the second half of that sentence is why CA-4 moved to daily on appliance components after a firmware event.

## 5. Testing the Measurement Itself

Every number above depends on the assertion layer being correct. An assertion that returns *pass* because its check is broken is worse than no assertion, because it manufactures confidence.

| Control | Implementation | Result in the period |
|---|---|---|
| **Negative testing of the assertion set** | Quarterly, a deliberate deviation is introduced on a staging twin of each baseline — a disabled audit setting, an added listener, a reintroduced default account — and the assertion is required to fail within its stated window | **6 baselines tested, 18 deviations introduced, 18 detected.** Two were detected later than their stated window and the windows were corrected rather than the results |
| Check-coverage reconciliation | Every SCS-01 to SCS-11 control maps to at least one CA check, and every CA check maps to at least one control; the mapping is asserted, not maintained | 11 of 11 controls covered; 0 orphan checks |
| Baseline-to-component reconciliation | Every component in the 12.5.1 inventory maps to exactly one baseline or to the recorded Class C position; reconciled monthly against four independent sources | 71 of 71; 0 unmapped, 0 double-mapped |
| Assertion-tool change control | A change to a CA check is a change record; a change that would **reduce** what a check tests requires CISO approval | 14 check changes; 2 reductions, both approved with reasons; 0 unapproved |

The two windows that were corrected rather than the results is the row worth reading. **When a negative test disagrees with the documented window, the honest move is to change the document.** The alternative — recording the detection as within window because it was close — is how an assurance layer becomes decorative.

## 6. Drift and Exception Handling

Drift and exception are different things and are handled by different routes. Conflating them is how an estate accumulates undocumented deviations that look like noise.

| | **Divergence (drift)** | **Exception** |
|---|---|---|
| What it is | The running state has moved away from the approved baseline without a decision | The approved baseline **cannot** be met on a named population, and that has been decided |
| Route | Incident. Remediate, then find the cause | Registered under 04.01 §8 with a justification, additional security features, owner and expiry |
| Who decides | Nobody — there is nothing to decide, the state is wrong | CISO for CDE components and for anything affecting 2.2.2, 2.2.5 or 2.2.7; Director of Infrastructure &amp; Network otherwise |
| Maximum life | The SLA | **12 months**, renewed only by re-approval with fresh evidence; a third renewal escalates to the PCI Steering Committee |
| What it never is | A reason to relax the baseline | A compensating control. **An exception is not a Compensating Controls Worksheet**, and none of Marketa's three worksheets is a configuration exception |

### 6.1 The register at 2026-07-15

| ID | Population | Item not met | Class | Owner | Expiry | Status |
|---|---|---|---|---|---|---|
| **SCS-EX-01** | 12 BL-APP appliances plus the 496 store appliances under NSC-EX-01 | SCS-06 — SNMPv3 unsupported, SNMPv2c retained read-only | Structural, vendor capability | Trevor Kim | 2027-06-30, quarterly review | Open; eliminated by **CAP-05** in the FY2027 refresh |
| **SCS-EX-02** | 9 CON-03 vendor-locked appliances | SCS-03, SCS-04, SCS-08 and SCS-10 cannot be asserted internally | Contractual | Trevor Kim | 2027-01-31, aligned to **CAP-06** | Open; §7 |
| **SCS-EX-03** | 1 vendor appliance management interface | SCS-11 partially — NTLM authentication | Vendor capability | Trevor Kim | 2027-01-31 | Open |
| **SCS-EX-04** | 6 BL-WIN Level 1 items on the CDE-06 desktop image | Relaxed to permit the dispute-image rendering path | Functional | Elena Marchetti | 2027-03-31 | Open |

**Four exceptions across 71 components**, unchanged since 04.01 published them, each with a named owner and a date. Two are the same constraint seen from different requirements, which is why they expire on the same date.

### 6.2 The relationship to the vulnerability exceptions

The `VE-nn` deferral register in 04.06 §4.3 and the `SCS-EX-nn` register here are deliberately separate. A configuration exception says *this setting cannot be applied on this population*. A vulnerability deferral says *this fix cannot be installed inside the freeze*. They are cross-referenced monthly, and a component appearing in both is escalated, because a component that is both unhardenable and unpatchable is not carrying two exceptions — it is carrying one problem described twice. **No component appeared in both registers in the period.**

## 7. What Cannot Be Measured the Standard Way

### 7.1 The nine CON-03 appliances — CAP-06

| Dimension | Position |
|---|---|
| Population | **9 of 71.** POS back-office appliances supplied and maintained under terms that prevent Marketa installing an agent or holding a privileged credential. Constraint **CON-03**, known before the programme started |
| Requirement 2 consequence | SCS-03, SCS-04, SCS-08 and SCS-10 cannot be asserted from inside. Verification changes from **assertion to observation** |
| What is measured instead | Unauthenticated service enumeration from an adjacent segment, weekly, asserted against the expected service set; firmware version read from the management console monthly and reconciled against the vendor's advisory feed; quarterly vendor configuration attestation under 12.8.5, reconciled against the observed service set; network reachability constrained and asserted by the Phase 03 controls |
| Result in the period | Observed service set matched expectation on **13 of 13 weekly enumerations**; firmware reconciled on 3 of 3 monthly checks; 1 vendor attestation received late by 9 days and chased |
| What the programme will **not** say | That any of this establishes baseline compliance. It establishes that the externally visible behaviour has not changed, which is a different and much weaker claim |
| Requirement 11 consequence | **11.3.1.2 authenticated internal scanning is Not in Place** — one of the two Not in Place findings in the ROC, remediation dated **2027-01-31** |
| Risk | **R-36**, High 16 |
| Corrective action | **CAP-06** — a contractual right to credentialed scanning and agent installation at the FY2027 renewal, or replace the platform. Owner Trevor Kim |

> **An appliance nobody can inspect is not an appliance that is secure. It is an appliance whose state is unknown, inside the assessed population, and the register says so.**

That sentence is carried unchanged from 04.01 §7 because softening it in a compliance-evidence document is exactly the temptation this document exists to resist. Nine of seventy-one components — **12.7% of the assessed population** — have their configuration state established by inference. That number belongs in any honest reading of the compliance rates in §3.

### 7.2 The six SaaS control planes

| Dimension | Position |
|---|---|
| Population | **6 of 71.** Vendor-hosted control planes where Marketa configures a tenant and cannot configure the platform |
| What Marketa asserts | The **tenant** configuration — authentication and federation settings, role assignments, session policy, data-residency and retention settings, API token inventory, audit-log export — through the provider's API where one exists, daily; by documented inspection where it does not, quarterly |
| What Marketa does not assert | The platform. There is no baseline because there is nothing Marketa can configure, which 04.01 §2 records rather than inventing a document to fill the row |
| Substituted assurance | **12.8.4** validation monitoring and **12.8.5** responsibility matrices, reviewed quarterly, with the provider's own assurance report examined rather than filed |
| Honest limit | A provider attestation is a statement about the provider's process. It is not an observation of Marketa's tenant, and the two are recorded as different evidence grades |

## 8. How This Will Be Sampled in November

QSA fieldwork runs **2026-11-02 to 2026-11-20**, inside the seasonal freeze, which means the assessor sees the estate in its stable state. Requirement 2's testing procedures examine configuration standards, interview personnel and **inspect system configurations to verify the standards are applied.** The last limb is a sample, and the evidence set is assembled to survive it.

| What the assessor is expected to do | What Marketa produces | The failure this would expose |
|---|---|---|
| Select a sample of components across platforms and zones | The 12.5.1 inventory with baseline mapping, from which the sample is drawn by the assessor, not offered by Marketa | A sample drawn from a curated list |
| Ask for the configuration standard for each sampled component | The baseline document, its source derivation, its version, and its deviation record with justifications and owners | A standard that exists in general but not for this platform |
| Compare the running configuration to the standard | The assertion record for that component for that date, plus the raw configuration extract the assertion read | An assertion layer that reports a verdict without retaining what it read |
| Ask when the standard was applied and how it was verified before production | The SCS-03 build-gate output and the first-boot assertion record for the component | Verification after the fact, which is what 2.2.1 specifically excludes |
| Look for a divergence and ask what happened | The divergence record, the incident, the remediation timestamp, and the cause analysis — **including all 74** | A clean chart with no incidents, which invites the question of what the control is doing |
| Test a negative — pick a setting and check it on the box | The item is in the machine-verifiable set, or it is in the 73-item inspection set with a date and an inspector | An item claimed but never verified. **04.01 §1's rule exists to make this outcome impossible** |
| Ask about the components that cannot be sampled that way | §7, the CON-03 constraint, SCS-EX-02, the substituted verification, CAP-06, and the 11.3.1.2 Not in Place finding | A gap presented as coverage |
| Ask who approved an exception and when it expires | The four-row register in §6.1 with approver and expiry | An exception with no owner, no date, or a life longer than the standard permits |

The seventh row is the one the programme has prepared for most carefully. **The assessor is told about the nine appliances by Marketa, in July, in writing, before fieldwork** — in the same way the QSA was told about the failed segmentation test on the day rather than discovering it in November. A constraint disclosed is a constraint being managed; a constraint discovered is a finding about the programme as well as about the appliance.
