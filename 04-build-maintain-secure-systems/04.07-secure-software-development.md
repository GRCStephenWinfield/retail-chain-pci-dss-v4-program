## Purpose

Requirement **6.2** — bespoke and custom software developed securely. This document covers **6.2.1** (secure development), **6.2.2** (annual training for software development personnel), **6.2.3** and **6.2.3.1** (review before release, and the manual review rules) and **6.2.4** (software engineering techniques preventing common attacks).

It also covers the pre-production data position under **6.5.5** — live PANs are never used for testing or development — because that control belongs with the development lifecycle even though the rest of the 6.5 change-management family is delivered in **04.08**. And it delivers two of the three preventive controls that Phase 02 promised would arrive in Phase 04 following finding **PAN-03**: pattern-based log redaction and the pipeline guardrail on production log levels. The third, the change-closure verification for temporary configuration changes, is 04.08's.

**6.4.3 payment-page script management is 04.10.** This document builds the pipeline that produces the payment page and can prove what it published. It does not make the claim about what executes in the consumer's browser; that claim needs different evidence and 04.10 provides it.

## 1. What Counts as Bespoke and Custom Software

Requirement 6.2 attaches to bespoke and custom software. Getting the population right is the first control, because a requirement applied to the wrong set of things is either theatre or a gap.

| In scope of 6.2 | Not in scope of 6.2 |
|---|---|
| The **storefront** and its checkout flow, including the pages that embed the Truvance iframe | The **Truvance hosted checkout iframe** — the provider's software, assured under 12.8 |
| The **6 payment page templates** and the build pipeline that publishes them | The **Verition POS application** — a validated P2PE solution, packaged software |
| **CDE-01** Payment Operations application | The **Cadence** suppression platform |
| **CDE-04** settlement reconciliation engine | The ERP, the warehouse management system and other packaged corporate applications |
| **CDE-07** refunds and adjustments service | Third-party libraries as **artefacts** — covered by 6.3.2 as inventory, not by 6.2 as development |
| The order orchestration service, the customer service console, the reporting extract service, the store special-order service | Infrastructure-as-code, which is governed by the change process in 04.08 — though it passes the same pipeline gates |
| **The 2 legacy batch integrations**, which nobody maintains and which therefore need the requirement most | |

Nine applications and two legacy integrations, matching the 6.3.2 inventory in 04.06 §2.1 exactly. **The two inventories are generated from the same source and asserted equal**, so a component cannot be in the vulnerability inventory and outside the development standard.

## 2. The Secure Development Lifecycle — 6.2.1

6.2.1 obliges bespoke and custom software to be developed securely: based on industry standards or best practices for secure development, in accordance with PCI DSS, and with information security considered at each stage of the lifecycle.

Marketa's lifecycle is derived from **OWASP ASVS** for the requirement set, **NIST SP 800-218** for the practice structure, and PCI DSS itself for the payment-specific obligations. It is expressed as gates rather than as guidance, because a stage of the lifecycle at which nothing can fail is not a stage.

| Stage | Security activity | Gate — what stops the work |
|---|---|---|
| **Requirements and design** | Security acceptance criteria attached to any story touching payment, authentication, authorisation or personal data, with abuse cases written alongside use cases. A **threat model** is required for any change to a payment flow, an authentication mechanism, a trust boundary or a data store, reviewed by the security engineering pairing rather than by a committee | A payment-path story with no security acceptance criteria cannot enter a sprint. No threat model, no design approval; 14 threat models produced in 2026 |
| **Build** | Static analysis, secret scanning, software composition analysis, infrastructure-as-code scanning, and the banned-primitive cryptography rules in §6 | Any High or Critical finding fails the build. Secret detection fails the build unconditionally |
| **Test** | Dynamic analysis against the deployed pre-production build; authorisation test suite; the security regression pack | A failing security regression is a release blocker with no override below the CISO |
| **Review** | Manual code review under §5, plus management release approval | Enforced by branch protection and by the release record |
| **Release** | Signed artefact under **K-08**; deterministic build; bill of materials emitted | An unsigned artefact will not deploy — the deployment controller verifies the signature |
| **Operate** | Logging to the Requirement 10 event set; the 6.3.1 intake; the 11.6.1 monitoring for payment pages | A production defect with a security cause returns to the threat model, not only to the backlog |

The three payment-path repositories — the payment page templates, CDE-07 and the checkout flow in the storefront — carry a stricter configuration of every gate: two reviewers instead of one, mandatory threat model on any change rather than on qualifying changes, and no emergency-merge path that skips review entirely.

## 3. Development Personnel and Training — 6.2.2

6.2.2 obliges software development personnel working on bespoke and custom software to be trained at least once every 12 months on software security relevant to their job function and development languages, including secure design and secure coding techniques, and including how to use any security testing tools in use.

| Element | Implementation |
|---|---|
| Population | **74 software development personnel** — 58 Marketa employees and 16 contractors — across e-commerce engineering, payment operations engineering and the platform team |
| Frequency | Annually, and within 30 days of joining for a new starter or a new contractor |
| Role-relevant content | Separate tracks by language and function: TypeScript and Node for the storefront and payment templates, Java for CDE-01 and CDE-04, Python for CDE-07 and the tooling, and a platform track covering infrastructure-as-code and pipeline security |
| Secure design | Threat modelling as a practical exercise against a Marketa payment flow, not a generic one |
| Secure coding | The five 6.2.4 attack classes in §6, each with a language-specific exercise and a code sample drawn from Marketa's own repositories |
| **Tooling** | How to read and act on the static analysis, composition analysis and dynamic analysis output — the limb of 6.2.2 that is most often skipped, and the one that determines whether the gates in §2 produce fixes or waivers |
| PCI-specific | What account data is, why the iframe matters, why a debug log level in production is a card-data incident, and the four findings from Phase 02 presented as case studies |

### 3.1 Training completion as a technical control

Completion is not tracked in a spreadsheet. **Commit access to any repository in the 6.2 population is conditional on current training**, revoked automatically when training lapses and restored automatically on completion.

| Measure | Result |
|---|---|
| Population, and completion by 2026-06-30 | 74; **74 of 74 — 100%** |
| Access suspensions triggered | **3 contractors**, suspended for a combined 11 days until they completed |
| Median time from assignment to completion, and new starters trained within 30 days | 9 days; 11 of 11 |

The three suspensions are reported because they are the evidence that the control is real. A training requirement whose only consequence is a reminder email produces a completion rate; a training requirement wired to repository access produces a completion rate **and** three people who found out it was wired that way.

## 4. Code Review Before Release — 6.2.3

6.2.3 obliges bespoke and custom software to be reviewed before release to production or to customers, to identify and correct potential coding vulnerabilities: reviews ensure code is developed according to secure coding guidelines, reviews look for both existing and emerging vulnerabilities, and appropriate corrections are implemented before release.

### 4.1 Automated review

| Tool class | Coverage | Gate |
|---|---|---|
| Static application security testing, and secret scanning | All 9 applications and both legacy integrations, on every pull request and every merge to the main branch; secret scanning includes full history on repository onboarding | High or Critical fails the build. Any secret detection fails the build unconditionally, and the credential is rotated before the build is retried |
| Software composition analysis | Every build; produces the 6.3.2 bill of materials as a by-product | A dependency with a Critical or High advisory fails the build unless an exception is registered |
| Infrastructure-as-code scanning | CT-30 and the 6 pipeline repositories | Boundary-affecting findings fail the build and raise a 1.2.2 review |
| Dynamic application security testing | Pre-production deployments of the storefront, the payment templates and CDE-07 | Findings triaged against the 6.3.1 ranking; High and Critical block release |

**Automated review is necessary and does not satisfy 6.2.3 on its own.** A scanner does not find a business-logic flaw, an access-control gap or a misuse of a correct cryptographic primitive, and those are three of the five classes 6.2.4 names.

### 4.2 Manual review — 6.2.3.1

6.2.3.1 applies where manual code reviews are performed before release. It obliges code changes to be reviewed by individuals **other than the originating author**, who are knowledgeable about code-review techniques and secure coding practices, and to be **reviewed and approved by management** before release.

Marketa separates two things the industry routinely conflates.

| | Peer review | Management release approval |
|---|---|---|
| What it is | A qualified engineer other than the author reads the change for correctness and security | An accountable manager approves that the change may go to production now |
| Who | A member of the reviewer pool — §4.3 | The engineering manager for the owning service; for payment-path repositories, Sonia Rendell or a named delegate |
| When | On the pull request, before merge | On the release, after all gates pass |
| Enforced by | Branch protection. **The platform will not accept the author's own approval**, and the payment-path repositories require two approvals from different reviewers | The release record, which the deployment controller requires before it will promote an artefact |
| Evidence | Pull request history with reviewer identity and timestamp | Release record with approver identity and timestamp |

Keeping them separate matters because 6.2.3.1 asks for both, and a single approval workflow that a manager happens to click satisfies neither cleanly: it is either a peer review performed by someone whose job is not to read code, or a management approval given by someone reviewing a diff rather than a release.

### 4.3 The reviewer pool

| Element | Rule |
|---|---|
| Membership | **29 engineers** across the four language tracks. Membership requires current 6.2.2 training plus a secure code-review module, and is reviewed annually |
| Payment-path subset | **11 reviewers** qualified to review the payment templates, the checkout flow and CDE-07 |
| Conflict rule | An engineer may not review a change to code they authored, and may not be the sole reviewer of a change authored by someone they line-manage |
| Coverage measure | 100% of merges to the main branch of an in-scope repository carry a non-author approval; enforced technically, so the measure is a property of the platform rather than a sampled statistic |

### 4.4 The emergency route

A production incident sometimes requires a fix faster than a full review cycle. The route exists, is narrow, and closes:

| Element | Rule |
|---|---|
| Trigger, and who approves | An active production incident at P1 or P2; engineering manager plus the on-call security engineer, both recorded |
| What is skipped | Only the pre-merge peer review. **The automated gates are never skipped** — a build that fails secret scanning does not deploy during an incident either |
| What follows | Full retrospective review within **2 business days**, findings raised as ordinary work, and the change re-examined at the incident post-mortem |
| Use in 2026 | 4 times; all four retrospectively reviewed inside the window; 1 produced a follow-up finding, a missing authorisation check on a new administrative endpoint, fixed the same week |

## 5. Preventing Common Attacks — 6.2.4

6.2.4 obliges software engineering techniques or other methods to be defined and in use to prevent or mitigate common software attacks. The requirement names five classes and adds a sixth limb covering high-risk vulnerabilities identified under 6.3.1.

The distinction that makes this requirement pass or fail is between a **guideline** and a **technique in use**. A coding standard saying "use parameterised queries" is a guideline. A lint rule that fails the build on a string-concatenated query is a technique in use.

| Attack class | Techniques in use | Enforcement |
|---|---|---|
| **Injection** — SQL, LDAP, XPath, command, parameter, object and fault injection | Parameterised queries and an ORM with raw-SQL construction disabled; allow-list input validation at the service boundary with schema-based request validation; context-aware output encoding; a Content Security Policy with nonces and no `unsafe-inline`; LDAP and XPath escaping via a single helper; shell execution prohibited outright in the payment-path services | SAST rules fail the build on raw query construction, on shell invocation in prohibited packages, and on unencoded output in a template. The CSP is asserted on every deployed page |
| **Attacks on data and data structures** — buffers, pointers, input data, shared data | Memory-safe languages by default across all 9 applications. Deserialisation restricted to an explicit allow-list of types, with polymorphic deserialisation disabled. Request size and depth limits at the edge. Immutable data structures in concurrency-sensitive paths | The one native dependency in the estate — an image processing library in the storefront — is pinned by hash, sandboxed in a restricted process, and fuzz-tested on version change. SAST rules fail the build on unsafe deserialisation patterns |
| **Attacks on cryptography usage** — weak, insecure or inappropriate implementations, algorithms, suites or modes | **A single approved cryptographic library per language, wrapped in a Marketa API** that exposes only authenticated encryption and vetted key handling. Keys are fetched from CT-14 at runtime and never read from configuration or source. Bespoke cryptography is prohibited without CISO approval, which has never been granted | A banned-primitive rule set fails the build on ECB mode, on MD5 and SHA-1 for security purposes, on hard-coded initialisation vectors, on non-cryptographic random sources in security contexts, and on **any client configured to skip certificate validation** — the control 04.04 §3 depends on |
| **Attacks on business logic** — abuse of features through APIs, protocols, channels or client-side functionality | Server-side enforcement of price, quantity, eligibility and refund limits, with **no trust in any client-supplied total**. Idempotency keys on every state-changing payment operation. Explicit state-machine validation on the order and refund lifecycles. Rate limiting and velocity checks on refund and adjustment endpoints. Abuse cases written at the requirements stage and turned into tests | Abuse-case tests run in the security regression pack. **Refund fraud is Marketa's live business-logic risk**, and CDE-07's refund path carries velocity limits, a value threshold requiring a second authorisation, and daily anomaly reporting to Payment Operations |
| **Attacks on access control** — bypassing or abusing identification, authentication or authorisation | Deny-by-default authorisation at a central policy enforcement point; object-level authorisation checked on every retrieval, not only at the route; no authorisation decision made in client code; session management standards covering rotation, fixation, timeout and secure cookie attributes; administrative endpoints separated and reachable only from the brokered path | An automated authorisation test suite runs every endpoint against every role including an unauthenticated principal, and fails the build on any unexpected success. **This suite exists because the application penetration test's second Critical finding was an unauthenticated admin interface on the chargeback application** |
| **High-risk vulnerabilities from 6.3.1** | The ranking output in 04.06 §1.2 feeds the technique set: a class of issue that appears in the intake becomes a rule, a test, or a training exercise | Reviewed quarterly by Sonia Rendell and Marcus Hale jointly; changes to the rule set are versioned with the pipeline |

The access-control row is deliberately blunt. The September 2026 application penetration test produced 11 findings, one of them Critical — an unauthenticated administrative interface. **A technique adopted because a tester found the gap is worth more in a portfolio than a technique adopted because a standard listed it**, and the honest sequence — finding first, control second — is recorded rather than smoothed.

## 6. The Payment-Page Build Pipeline

The 6 payment page templates are the highest-value artefact Marketa builds, and **R-01** — unauthorised script executing in the consumer browser on a payment page — is the register's highest-scored risk at 20.

| Control | Implementation |
|---|---|
| Deterministic build | The same source produces the same artefact hash. A build that is not reproducible is a build whose contents cannot be attested |
| No inline script | Every script is an external file with a Subresource Integrity hash. The Content Security Policy uses nonces and forbids `unsafe-inline` and `unsafe-eval` |
| First-party integrity | Every first-party script carries an SRI hash generated at build time and embedded in the template |
| Artefact signing | The published bundle is signed with **K-08** from CT-17, and the deployment controller refuses an unsigned or mis-signed artefact |
| Publication record | Every publication writes an immutable record — artefact hash, script manifest, signer, approver, timestamp — retained and queryable |
| Reconciliation | The published script manifest is reconciled against the **6.4.3** inventory. A script in the manifest that is not in the inventory, or the reverse, is a finding |
| Who can publish | Only the pipeline identity. **No human has write access to the payment-page origin**, which is asserted daily by CA-2 |
| Tag manager | Constrained by an allow-list of destinations enforced in the CSP. The container cannot inject a script from an undeclared origin, which is the specific mechanism that produced the 3 unauthorised scripts at first inventory |

> **The pipeline can prove what Marketa published. It cannot prove what executes.**
>
> A third-party script loaded from a vendor's origin can change after publication without any Marketa artefact changing. That is a different claim, it requires different evidence, and **04.10** makes it under 6.4.3 with 11.6.1 change- and tamper-detection alerting within 24 hours. This document stops at the boundary deliberately, because the most common failure in payment-page assurance is a build attestation presented as though it were a runtime one.

## 7. Dependency Management

| Control | Detail |
|---|---|
| Lockfiles | Mandatory. Every dependency is pinned to a version **and a hash** |
| Internal proxy | All package resolution goes through an internal registry proxy. **No build reaches a public registry directly**, so a build cannot be affected by a registry outage or by a package that appears and disappears |
| Quarantine | A newly published version of any package is held for **48 hours** before it becomes resolvable internally. This defeats the compromised-release and typosquatting window, which is measured in hours far more often than in days |
| Allow-list for new direct dependencies | A new direct dependency requires review — maintenance status, release history, maintainer count, licence, and whether the functionality justifies the surface. **63 components with no upstream activity in 24 months** were found at the first 6.3.2 inventory; the review exists so the number does not grow |
| Composition analysis gate | Critical and High advisories fail the build |
| Bill of materials | CycloneDX emitted per build as an immutable artefact — this is the 6.3.2 inventory's source, per 04.06 §2.2 |
| Container base images | Built from a small set of Marketa-maintained base images, rebuilt weekly, so a base-image fix reaches every workload through one change rather than through nine |

## 8. Logging, Redaction and the PAN-03 Controls

Phase 02 recorded three preventive changes arising from finding PAN-03 — a 1.4 GB debug log containing 1,143 PAN instances, written for seven months because a temporary log level was never reverted — and stated that all three would be delivered in Phase 04. Two are here.

| Control | Implementation | Status |
|---|---|---|
| **Pattern-based log redaction replacing the field-name deny-list** | Redaction is applied in the logging library at the point of emission, by **pattern** — Luhn-validated candidate account numbers, track-data structures, verification-code shapes and PIN-block shapes — rather than by field name. A field called `cardNumber`, `acctNo`, `pan` or anything else is redacted because of what it contains, not because of what it is called. The redaction library is a mandatory dependency for every application in the 6.2 population, enforced by a build rule | **Live**, all 9 applications and both legacy integrations |
| **Pipeline guardrail on production log levels** | Any deployment configured with a `DEBUG` or `TRACE` log level for a production environment is rejected at the deployment controller. The rejection is not overridable by the deploying engineer; raising the level in production requires a change record with an explicit revert action and an expiry | **Live** |
| Change-closure verification for temporary configuration changes | A temporary change must carry a revert action with a verification step, and the change cannot close until the revert is verified | **04.08** — delivered with the 6.5.1 change process |

A fourth control was added that Phase 02 did not ask for: **log-content sampling.** A sample of production log output from each application is scanned weekly by the same discovery pipeline that runs against the estate. It has produced no account-data hits, and it is the control that would catch a redaction library that has been silently bypassed — which is the failure mode the deny-list taught the organisation to expect.

## 9. Pre-Production Data — 6.5.5

6.5.5 obliges that **live PANs are not used for testing or development.** In an estate where live PAN barely exists in production, the obvious question is how it could reach a test environment at all — and the answer, from PAN-02 and PAN-04, is that account data arrives from outside the systems that are supposed to hold it.

| Control | Implementation |
|---|---|
| **Synthetic test data only** | Test card data is generated from the card brands' published test ranges. The generator is the only sanctioned source and is available to every developer, so the compliant route is also the convenient one |
| Environment separation | Pre-production environments are separated from production with distinct networks, distinct credentials and distinct roles — the 6.5.3 and 6.5.4 controls, delivered in 04.08 and referenced here |
| **No production data copy path** | There is no technical route to copy production data to a lower environment. No shared credential, no network path from a pre-production environment into Z1 or Z2, and a backup restore path whose target is constrained to production and which requires dual authorisation |
| Provider sandboxes | Truvance and Cadence sandbox environments are used for integration testing, and neither accepts a live account number |
| Test accounts | Removed before production release under 6.5.6, asserted by the deployment gate |
| **Discovery over pre-production** | The Phase 02 discovery pipeline runs quarterly against every pre-production environment, not only against production. **This is the control that makes 6.5.5 evidenced rather than asserted** |

### 9.1 What the first pre-production discovery run found

**Zero account data.** And 2,140 real customer names and email addresses in a seeded dataset for the customer service console, copied from a production export in 2023 by a process nobody remembered.

That is not a PCI DSS finding. It is exactly the same failure mode as finding PAN-02 — a copy of real data made for a legitimate short-term purpose, left behind when the purpose ended, in a repository with no owner and no retention rule. It was reported to the General Counsel, the dataset was replaced with synthetic records, and the seeding process was rewritten to generate rather than copy.

The programme records it here because **the value of running a card-data discovery pipeline over pre-production is not only the card data it finds.** It is the demonstration that the class of failure is still present in the organisation, in a place where nobody was looking, five months after four instances of it were remediated with great ceremony.
